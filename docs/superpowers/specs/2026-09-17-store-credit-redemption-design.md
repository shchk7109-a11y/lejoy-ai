# 乐享 AI 积分兑换码与充值分期设计

日期：2026-09-17
状态：产品方案已确认，待设计稿审阅
目标分支：`codex/m4-release-ready`

## 1. 背景与目标

当前小程序已有新用户初始 100 积分、AI 功能扣分、失败返还、余额和流水查询；没有面向用户的持续获取积分方式。管理员账号也照常扣分，余额用完后需经审计补充，不能因管理员身份无限使用。现有人工加分入口保留，但加分及流水写入须改为同一数据库事务。

本设计分两期：

1. **本期实施：总部下发兑换码，店长免费赠给顾客，顾客在小程序兑换积分。** 店长向总部申请或购买码的库存、付款、总部确认均在线下完成，不在小程序内交易。
2. **后续单独立项：顾客在线付费充值。** 微信支付能力、数字积分的准入条件、价格、退款及对账方案未确认前，不显示充值价格、购买按钮或支付入口，不接入模拟支付。

不改变 AI 功能现有扣分价格和新用户赠分数额；不自动给任何现有账号补分。新功能不得把线下店长采购误表述为顾客可购买兑换码：店长向顾客发码是免费到店权益，禁止转售。

## 2. 角色与权限

| 角色 | 本期能力 | 明确不提供 |
| --- | --- | --- |
| 总部管理员 | 在现有 Web 管理后台维护门店、创建批次、确认线下结算后激活并一次性导出兑换码、停用未兑换码、查看门店库存和审计记录 | 未经身份核验的自动提权；绕开积分扣费 |
| 店长 | 在线下向总部申请库存、完成线下结算、接收总部交付的码，免费发给顾客 | 在系统里生码、改面额、激活批次、给自己或顾客直接加分、在小程序内采购 |
| 顾客 | 在小程序查看余额/流水，输入兑换码领取积分 | 付费充值入口、查询其他人的码或账户 |

现有 `users.role=admin` 只作为总部后台的候选权限标识；上线前仍要核对具体微信账号与后台登录身份。首次授权由受控运维命令执行并留操作记录，不能把“微信平台管理员”自动等同于本应用总部管理员。本期不新增店长登录角色或店长后台；其库存申请、对账和交付由总部在线下完成。

## 3. 业务流程

### 3.1 总部配码

1. 店长在线下向总部提出门店、数量和面额需求，线下付款或取得总部批准的赠送额度。
2. 总部后台新建**待确认批次**，记录门店、每码积分、数量、到期时间、用途、经办人和外部结算凭证编号；不在系统保存付款密码、账户资料或凭证图片。待确认批次不可兑换，也没有可交付码。
3. 总部核实线下结算后，由另一项明确的“确认并生成”操作激活批次，生成不可预测的一次性兑换码，并立即提供一次性 CSV 下载。管理员确认已安全交付店长。若 CSV 下载丢失，由总部停用该批次未兑换码、审计原因并重新配发；系统不提供明文码重复查看。
4. 总部可按门店查看已分配、已兑换、未兑换、已过期或已停用数量及积分总额。已兑换记录不可撤销；停用只影响尚未兑换的码。

总部可批准无需店长付款的活动赠码，但必须明确标记 `promotion`，记录审批人和原因；不能伪装成已付款采购。店长对顾客始终免费发码。

### 3.2 顾客兑换

顾客从首页余额或“我的”进入“积分中心”，看到当前余额、获取积分说明、兑换码输入框、全宽大按钮和积分流水。输入可接受大小写及分组连字符，提交前归一化；仅登录用户可兑换。服务端一次事务内完成：校验批次和码状态 → 抢占未使用码 → 原子增加用户余额 → 写入一条兑换流水 → 绑定兑换用户和时间。成功返回新增积分及新余额；重复提交同一码绝不再次加分。

错误态分别用大字说明“兑换码不正确”“已被使用”“已过期”“暂未生效或已停用”；不透露使用者身份。余额不足时，原有 AI 生成页引导到积分中心，不再展示现有的运营配置占位文案。无兑换码的用户可了解“到店向店长领取”，但不能看到不存在的线上付费充值入口。

### 3.3 管理员零余额

管理员的 AI 请求仍正常扣分。现有账号余额为零时，总部先核对应用内用户身份，再由授权人员通过现有人工加分入口发放一笔**明确数额**的测试或运营积分；操作者、目标用户、数额、原因及时间必须可审计。不得因本设计获批而擅自为当前账号充值，也不新增“管理员无限积分”开关。

## 4. 数据、事务与接口

本期允许的最小数据扩展：

- `stores`：门店 ID、名称、启用状态；门店 ID 是批次统计的稳定键。
- `credit_code_batches`：门店 ID、面额、数量、有效期、用途（采购或活动）、外部凭证编号、`pending/active/revoked` 状态、创建/确认/停用操作者和时间。
- `credit_codes`：批次 ID、唯一的码哈希、`unused/redeemed/revoked` 状态、兑换用户和时间。明文只在首次生成时交付，不落数据库、日志或后续查询接口。
- `credit_code_batch_events`：创建、确认、激活、导出、停用等操作的操作者、时间、批次、数量和原因；不含明文码及付款敏感数据。
- 扩展现有 `credit_transactions` 的类型或明确标记为 `code_redeem`，每次成功兑换恰好一条正向流水，可追溯批次与兑换码记录；人工补分也必须与余额变动同事务写流水。

兑换码由安全随机数生成，采用去歧义的 12 位大写字符、`XXXX-XXXX-XXXX` 展示；服务端只保存归一化码的 SHA-256 哈希，数据库唯一索引防碰撞。总部单批数量上限 1000，面额必须是正整数、有效期晚于激活时间；具体运营面额不写死在代码中，由总部创建时填写。生成前逐项校验并在单个数据库事务内落下批次、码及事件；激活后不可改面额、门店、数量或有效期，需要更正时停用未用码、重建批次。

建议接口（最终路径遵循项目现有 `/api/mp` 与 Web 管理路由组织）：

| 用途 | 请求/返回要点 |
| --- | --- |
| 顾客兑换 `POST /api/mp/credits/redeem` | `{ code }`；成功返回 `awardedCredits`、`balance`、`transactionId`；失败返回稳定错误码，不改余额 |
| 顾客资料/流水 | 复用现有 `/user/me` 与 `/credits/history`，补充兑换来源展示 |
| 总部批次管理 | 创建待确认、确认激活并一次性导出、停用、按门店列出库存和事件；每个操作都执行服务端管理员鉴权 |

管理员请求不能仅依赖前端隐藏按钮。兑换接口按用户和来源限速，连续猜码有冷却提示；数据库层有唯一哈希、行条件更新及事务，客户端双击、网络重发和并发请求均只可成功一次。生成/导出/兑换日志仅写批次 ID、用户 ID、状态、数量和耗时，不写明文码、输入内容或完整 CSV。

## 5. 页面与适老化

- “积分中心”显示大字余额、兑换码入口、最近流水和三句清晰说明：“新用户有初始赠分”“到店可领取店长赠送的兑换码”“目前暂不支持在线充值”。
- 兑换码可复制粘贴；每 4 位分组只用于显示，不强迫老人手工输入连字符。按钮、输入框、错误提示沿用现有适老化令牌，大触控区、高对比度、文字不单靠颜色传达状态。
- 兑换成功立即刷新余额和流水，失败保留输入并指出可采取的下一步；网络错误允许用户主动重试，服务端仍保证同一码只入账一次。
- 总部 Web 页面显示门店/批次状态、库存计数、一次性导出提醒和停用确认；不得把码清单长期展示在页面上。

## 6. 后续付费充值的门槛

第二期开始前，先核实微信小程序与商户号绑定、所售数字积分的支付准入、经营主体、价格及退款规则。届时另设订单和支付事件，只有服务端验证支付回调或主动查单确认为成功后，才以订单号幂等入账；前端支付成功回调不能直接加分。退款、对账、异常订单与发票/税务流程另行设计。本期不预埋假订单、不放出不可用的支付入口。

## 7. 验收与发布边界

自动化测试至少覆盖：未授权者不能配码/停用；待确认批次不可兑换；有效码只给一名用户入账一次；并发/重复提交无重复流水；错误、过期、停用、已用均不加分；余额和流水一致；人工补分事务失败时不留下半笔账；门店库存计数正确；无明文码进入数据库或日志；小程序没有付费入口。

发布前备份数据库并执行受控迁移；先在测试环境用两位用户并发兑换同一码，再做门店批次和适老化真机验收。生产授权、管理员身份核对、运营面额和第一批码分配须单独确认。部署完成后核对健康检查、余额/流水、库存计数及日志脱敏；测试通过或 HTTP 200 均不能代替真实顾客兑换验收。

## 8. 已确定与待后续决策

已确定：总部唯一生码和配额控制；店长线下向总部申请/结算且免费发顾客；顾客通过码领取积分；管理员不免扣费；微信支付未开通前不提供付费充值。

后续运营决策：实际面额、门店名单、码有效期、赠码活动审批人、管理员测试积分发放数额，以及付费充值的定价和上线资格。这些值在本期通过总部操作设置或上线前人工确认，不在代码中猜定。
