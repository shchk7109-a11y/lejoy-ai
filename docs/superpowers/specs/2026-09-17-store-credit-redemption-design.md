# 乐享 AI 积分兑换码与充值分期设计

日期：2026-09-17
状态：产品方案已确认，待设计稿审阅
目标分支：`codex/m4-release-ready`

## 1. 背景与目标

当前小程序已有新用户初始 100 积分、AI 功能扣分、失败返还、余额和流水查询；没有面向用户的持续获取积分方式。管理员账号也照常扣分，余额用完后需经审计补充，不能因管理员身份无限使用。仓库虽有旧版 H5 `/admin` 页面和 tRPC 管理接口，但生产缺少它依赖的 OAuth 登录配置，不能视为已建成、可使用的总部 Web 后台。本期须一并建设可独立登录的轻量总部后台。现有受控命令行人工加分能力保留，但加分及流水写入须改为同一数据库事务。

本设计分两期：

1. **本期实施：总部 Web 后台登录、配码、导出和查库存；店长免费赠给顾客，顾客在小程序兑换积分。** 店长向总部申请或购买码的库存、付款、总部确认均在线下完成，不在小程序内交易。
2. **后续单独立项：顾客在线付费充值。** 微信支付能力、数字积分的准入条件、价格、退款及对账方案未确认前，不显示充值价格、购买按钮或支付入口，不接入模拟支付。

不改变 AI 功能现有扣分价格和新用户赠分数额；不自动给任何现有账号补分。新功能不得把线下店长采购误表述为顾客可购买兑换码：店长向顾客发码是免费到店权益，禁止转售。

## 2. 角色与权限

| 角色 | 本期能力 | 明确不提供 |
| --- | --- | --- |
| 总部管理员 | 登录本期新建的总部 Web 后台，维护门店、创建批次、确认线下结算后激活并一次性导出兑换码、停用未兑换码、查看门店库存和审计记录 | 未经身份核验的自动提权；绕开积分扣费 |
| 店长 | 在线下向总部申请库存、完成线下结算、接收总部交付的码，免费发给顾客 | 在系统里生码、改面额、激活批次、给自己或顾客直接加分、在小程序内采购 |
| 顾客 | 在小程序查看余额/流水，输入兑换码领取积分 | 付费充值入口、查询其他人的码或账户 |

总部 Web 管理员使用独立的后台身份，不依赖旧版 H5 的 Manus OAuth，也不把 `users.role=admin` 或“微信平台管理员”自动视作总部后台权限。总部管理员如使用小程序，仍是一个正常扣分的用户；两种身份不因名称相同而自动关联。本期不新增店长登录角色或店长后台；其库存申请、对账和交付由总部在线下完成。

### 2.1 本期新建的总部后台与登录

同源 HTTPS 地址 `https://api.hxzhineng.xyz/hq` 提供轻量 Web 页面，服务端接口位于 `/api/hq/*`。复用现有 React 构建与 Express 部署，但**认证链完全独立**：旧 `/admin` 页面和 tRPC `admin` 鉴权不能作为新后台的安全依据；旧 `/admin` 入口提示迁移到 `/hq`，不自动继承旧登录状态。后端只在验证总部会话后允许配码、导出、停用、库存与审计查询。

后台采用总部账号密码加动态验证码（TOTP）双因素登录。总部账号由受控服务器命令首次创建，随机初始密码及 TOTP 绑定信息仅向现场操作者展示一次，不写入仓库、部署日志或聊天；首次登录只允许修改初始密码，完成后才开放配码操作。密码使用加盐的 `scrypt` 哈希保存，TOTP 秘钥使用 AES-GCM 与服务器独立密钥加密保存；密钥文件仅 root 可读。丢失动态验证码设备时，只能由受控服务器命令核实身份后重置 TOTP，并撤销该账号全部会话，操作留审计。会话使用服务端存储的随机令牌哈希，浏览器只持有 `HttpOnly`、`Secure`、`SameSite=Strict` Cookie，30 分钟闲置或 8 小时到期并可主动退出。登录提交校验同源请求，所有已登录写操作校验 CSRF；登录按账号和来源限速，连续失败暂时锁定，失败提示不泄露账号是否存在。管理员停用后其会话立即失效。

界面只做本期必需的登录、门店、批次、导出、库存和操作记录；不把旧版模型密钥管理功能接到新会话上。页面可复用旧 H5 的布局组件，不复用其不可用的 OAuth 流程。本期不另建域名或独立服务。

## 3. 业务流程

### 3.1 总部配码

1. 店长在线下向总部提出门店、数量和面额需求，线下付款或取得总部批准的赠送额度。
2. 总部后台新建**待确认批次**，记录门店、每码积分、数量、到期时间、用途、经办人和外部结算凭证编号；不在系统保存付款密码、账户资料或凭证图片。待确认批次不可兑换，也没有可交付码。
3. 总部核实线下结算后，由另一项明确的“确认并生成”操作激活批次，生成不可预测的一次性兑换码，并立即提供一次性 CSV 下载。管理员确认已安全交付店长。若 CSV 下载丢失，由总部停用该批次未兑换码、审计原因并重新配发；系统不提供明文码重复查看。
4. 总部可按门店查看已分配、已兑换、未兑换、已过期或已停用数量及积分总额。已兑换记录不可撤销；停用只影响尚未兑换的码。

总部可批准无需店长付款的活动赠码，但必须明确标记 `promotion`，记录审批人和原因；不能伪装成已付款采购。店长对顾客始终免费发码。

### 3.2 顾客兑换

顾客从首页余额或“我的”进入“积分中心”，看到当前余额、获取积分说明、兑换码输入框、全宽大按钮和积分流水。输入可接受大小写及分组连字符，提交前归一化；仅登录用户可兑换。服务端一次事务内完成：校验批次和码状态 → 抢占未使用码 → 原子增加用户余额 → 写入一条兑换流水 → 绑定兑换用户和时间。成功返回新增积分及新余额；重复提交同一码绝不再次加分。

错误态分别用大字说明“兑换码不正确”“已被使用”“已过期”“暂未生效或已停用”；不透露使用者身份。余额不足时，原有 AI 生成页引导到积分中心，不再展示现有的运营配置占位文案。无兑换码的用户可了解“到店向店长领取”，但不能看到不存在的线上付费充值入口。

### 3.3 管理员零余额

管理员的 AI 请求仍正常扣分。现有账号余额为零时，总部先核对应用内用户身份，再由授权人员通过受控命令行人工加分入口发放一笔**明确数额**的测试或运营积分；操作者、目标用户、数额、原因及时间必须可审计。新 Web 后台本期不新增任意给用户加分的按钮，以兑换码为主要赠送方式。不得因本设计获批而擅自为当前账号充值，也不新增“管理员无限积分”开关。

## 4. 数据、事务与接口

本期允许的最小数据扩展：

- `hq_admin_accounts`：独立的总部账号 ID、登录名、密码哈希、加密的 TOTP 秘钥、首次改密标记和停用状态；不与小程序 `users.role` 自动关联。
- `hq_admin_sessions`：会话令牌哈希、账号 ID、最近活动时间、绝对过期时间和撤销状态；原始会话令牌只发给浏览器 Cookie。
- `stores`：门店 ID、名称、启用状态；门店 ID 是批次统计的稳定键。
- `credit_code_batches`：门店 ID、面额、数量、有效期、用途（采购或活动）、外部凭证编号、`pending/active/revoked` 状态、创建/确认/停用操作者和时间。
- `credit_codes`：批次 ID、唯一的码哈希、`unused/redeemed/revoked` 状态、兑换用户和时间。明文只在首次生成时交付，不落数据库、日志或后续查询接口。
- `credit_code_batch_events`：创建、确认、激活、导出、停用等操作的操作者、时间、批次、数量和原因；不含明文码及付款敏感数据。
- 扩展现有 `credit_transactions.type` 增加 `redeem`，并新增可空、唯一的 `creditCodeId` 关联码记录；每次成功兑换恰好一条 `redeem` 正向流水，可追溯批次与兑换码记录；人工补分也必须与余额变动同事务写流水。

兑换码由安全随机数生成，采用去歧义的 12 位大写字符、`XXXX-XXXX-XXXX` 展示；服务端只保存归一化码的 SHA-256 哈希，数据库唯一索引防碰撞。总部单批数量上限 1000，面额必须是正整数、有效期晚于激活时间；具体运营面额不写死在代码中，由总部创建时填写。生成前逐项校验并在单个数据库事务内落下批次、码及事件；激活后不可改面额、门店、数量或有效期，需要更正时停用未用码、重建批次。

接口按小程序和总部后台分开：

| 用途 | 请求/返回要点 |
| --- | --- |
| 顾客兑换 `POST /api/mp/credits/redeem` | `{ code }`；成功返回 `awardedCredits`、`balance`、`transactionId`；失败返回稳定错误码，不改余额 |
| 顾客资料/流水 | 复用现有 `/user/me` 与 `/credits/history`，补充兑换来源展示 |
| 总部登录 `POST /api/hq/auth/login` | 用户名、密码、动态验证码；成功设置专用安全 Cookie；失败统一提示并限速 |
| 总部登出 `POST /api/hq/auth/logout` | 撤销当前会话；写操作还需 CSRF 校验 |
| 总部批次管理 `/api/hq/*` | 创建待确认、确认激活并一次性导出、停用、按门店列出库存和事件；每个操作都验证总部会话、权限和 CSRF |

管理员请求不能仅依赖前端隐藏按钮。兑换接口按用户和来源限速，连续猜码有冷却提示；数据库层有唯一哈希、行条件更新及事务，客户端双击、网络重发和并发请求均只可成功一次。生成/导出/兑换日志仅写批次 ID、用户 ID、状态、数量和耗时，不写明文码、输入内容或完整 CSV。

## 5. 页面与适老化

- “积分中心”显示大字余额、兑换码入口、最近流水和三句清晰说明：“新用户有初始赠分”“到店可领取店长赠送的兑换码”“目前暂不支持在线充值”。
- 兑换码可复制粘贴；每 4 位分组只用于显示，不强迫老人手工输入连字符。按钮、输入框、错误提示沿用现有适老化令牌，大触控区、高对比度、文字不单靠颜色传达状态。
- 兑换成功立即刷新余额和流水，失败保留输入并指出可采取的下一步；网络错误允许用户主动重试，服务端仍保证同一码只入账一次。
- 总部 Web 页面含独立登录、首次修改密码、门店列表、批次创建及确认、库存计数、操作记录、一次性导出提醒和停用确认；不得把码清单长期展示在页面上。动态验证码在受控开户时绑定，登录失败时不暴露内部权限或凭证。

## 6. 后续付费充值的门槛

第二期开始前，先核实微信小程序与商户号绑定、所售数字积分的支付准入、经营主体、价格及退款规则。届时另设订单和支付事件，只有服务端验证支付回调或主动查单确认为成功后，才以订单号幂等入账；前端支付成功回调不能直接加分。退款、对账、异常订单与发票/税务流程另行设计。本期不预埋假订单、不放出不可用的支付入口。

## 7. 验收与发布边界

自动化测试至少覆盖：总部登录密码/TOTP 错误、限速、会话过期、登出、停用账号与 CSRF 拦截；旧 H5 登录状态不能访问新接口；未授权者不能配码/停用/导出；待确认批次不可兑换；有效码只给一名用户入账一次；并发/重复提交无重复流水；错误、过期、停用、已用均不加分；余额和流水一致；人工补分事务失败时不留下半笔账；门店库存计数正确；无明文码、初始密码或 TOTP 秘钥进入数据库明文或日志；小程序没有付费入口。

发布前备份数据库并执行受控迁移；先在测试环境验证总部登录、首次改密、会话/CSRF 和两位用户并发兑换同一码，再做门店批次和适老化真机验收。生产首次开户、管理员身份核对、运营面额和第一批码分配须单独确认。部署完成后核对健康检查、后台登录和权限、余额/流水、库存计数及日志脱敏；`/hq` 返回 HTTP 200 或静态页面可打开，均不能代替真实登录与顾客兑换验收。

## 8. 已确定与待后续决策

已确定：本期新建可登录的轻量总部 Web 后台；总部唯一生码和配额控制；店长线下向总部申请/结算且免费发顾客；顾客通过码领取积分；管理员不免扣费；微信支付未开通前不提供付费充值。

后续运营决策：实际面额、门店名单、码有效期、赠码活动审批人、管理员测试积分发放数额，以及付费充值的定价和上线资格。这些值在本期通过总部操作设置或上线前人工确认，不在代码中猜定。
